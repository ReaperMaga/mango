# Mango

A desktop workbench for coding agents. Open a project, run several Claude Code
and Codex chats side by side, and keep a real terminal docked at the bottom.

Built with Rust + [Tauri 2](https://tauri.app) and [Nuxt 4](https://nuxt.com) (SPA).

**Documentation:** [reapermaga.github.io/mango](https://reapermaga.github.io/mango/): install, guides and development notes.

## Status

- **Projects:** open a folder, create a project (with `git init`, a Lore repository, or no version control), clone a repository with live git progress (or a `lore://server/repository` with the Lore CLI), recent projects. The project menu is one list of projects, each with its branch underneath (or, with a server mark, the environment it runs in), and widens to fit long names: first the projects open in that window, marked with a dot (the active one is checked), then up to eight recent ones, so a window opened on one project can still reach the others (one open in another window says so and brings that window to the front). Hovering a row shows a window button that opens that project in a new window (`Shift+Enter` from the keyboard), and the × that closes an open one or takes a recent one off the list (or Delete).
- **Agents:** real Claude Code and Codex runs. Mango starts your installed `claude` / `codex` CLI for each turn, streams text, thinking and tool calls (runs of steps fold into one summary line, such as "Ran 3 commands, read 2 files", that opens on click), shows diffs and command output, ends each reply with the files it changed (a folder tree with added and removed lines per file and folder; a click opens the file's diff, or the file once its changes are committed, and "Review" opens Changes), and asks you before edits and commands (per the chat's permission mode: Plan, Ask first, Accept edits, Full auto). When an agent asks you something (Claude Code's multiple-choice questions, Codex's questions, or a form or sign-in link from one of their MCP servers), it shows as a card in the chat: pick options, type your own answer, then Answer or Dismiss; the chat shows "Needs your answer" meanwhile, and secret answers are never saved with the chat. Conversations resume across turns and app restarts. One chip under the message box (agent, model, effort and permissions, such as "Opus 5.5 · High · Ask first") opens a menu, one step at a time: each agent opens its models, Effort a slider, Permissions the four modes (arrow keys work throughout, Esc steps back). The model lists show every model the installed CLI offers your account (asked from the CLI itself, without running a turn, and cached) and scroll when they are long. Picking another agent's model moves the chat to that agent; in a chat that has already started, the new agent begins a fresh conversation without the earlier messages (the menu says so), and the switch waits while a run is going. Effort is per chat (Claude Code: low to max; Codex: the levels its model accepts); with no level picked the menu shows the level the CLI will use (Claude Code's from your settings, Codex's per model), else "Default". You can keep writing while an agent works: the message waits in a queue above the input and goes out as the next turn once the run finishes, so the agent is not disturbed. "Send now" on a queued message hands it to the running turn instead (the agent reads it at its next step; if the run can't take it, it still goes out as the next turn). Stop keeps the queue but sends nothing until you send a message again or press "Send now".
- **Working with messages:** every message shows when it was sent (hover for the date; a message that waited in the queue also says when you wrote it) and a row of buttons on hover: copy, pin, branch, and, on your messages, edit; on replies, ask again. A code block has its own Copy button. A reply ends with what it cost: tokens in (cached ones included) and out, and the price when the CLI reports one (Claude Code does; Codex shows tokens only). Edit replaces one of your messages and everything after it and runs it again; ask again does the same for the message before a reply (it asks twice when more than that exchange would go). Neither CLI can rewind a session, so the agent starts a fresh one and gets the earlier messages as text (words and attached file names, not tool calls). Branch makes a new chat from a message on (same folder, agent and settings) the same way. Pinned messages are listed under "Pinned" in the message list. In a chat: find with `Ctrl/⌘ F` (Enter and Shift+Enter step through the hits; rows folded into a step summary are not searched), the message list button jumps to anything you asked or pinned, days are marked between messages, "Jump to latest" shows when you scrolled up, and Arrow Up in an empty message box brings back what you sent before (Arrow Down returns).
- **Background tasks and sub-agents (Claude Code):** commands the agent starts in the background (or that outlive their timeout) and sub-agents nobody waits for are listed above the composer while they run, with how long each has run, a peek at a command's output and a stop button. The run stays open until they finish, and when one does, Claude Code picks it up by itself in a new reply that says what finished. Each sub-agent gets a read-only chat of its own, nested under the chat that started it in the sidebar (sub-agents of sub-agents nest further), opened from there or from the "Open" link on its Delegated row.
- **Slash commands:** type `/` at the start of a message to list the commands of the chat's agent, filtered as you type (arrows to move, Tab to complete, Enter to run or complete, Esc to close). Claude Code's list comes from the CLI itself, so it includes its built-ins that work outside the terminal UI (`/compact`, `/context`, `/code-review`, …) and your own commands and skills. For Codex, Mango runs `/review` (the uncommitted changes, or your instructions), `/compact` and `/init` through the Codex app-server, and lists your Codex skills. `/clear` is Mango's own for both: the chat starts a new conversation and the agent forgets the messages above. `/create-pr` is Mango's too: the agent follows the project's own conventions to commit the work on the branch (on a new branch if you are on the default one), run the project's checks, push, and open a GitHub pull request with `gh` (a GitLab merge request with `glab` when the project is on GitLab), then reports the link and how each check went. Notes after the command go along (`/create-pr draft, mention the migration`). The new pull request is linked to the chat. `/create-release` does the same for a release: from an up-to-date default branch with green CI, the agent picks the next version (semver from the commits since the last release, or the one your notes name), sets it with the project's own tooling, runs the checks, commits, tags and pushes, then publishes the GitHub release with `gh` or the GitLab release with `glab` (or, when a workflow or pipeline publishes on the tag push, points you to that run). It stops instead of releasing uncommitted work or force-pushing (`/create-release minor`, `/create-release 2.0.0-beta.1, pre-release`). A command sent while the agent works waits and runs as a turn of its own.
- **Files (tool window on the right):** the project's folders as a tree, with git status and excluded files (ignored by git, or excluded by you) dimmed. The view options in its header show or hide excluded files and dotfiles, put folders that hold only one folder on a single row (`src/main/java`), sort by name or file type, keep folders on top or not, and keep the open file selected; the target button selects it once. "Show in Files" finds a file even when it is hidden. Right-click a file or folder, or the empty space and header for the project folder itself, to create a file or folder, rename (`F2`), duplicate a file, show it in Explorer, Finder or the file manager, open a terminal there, or delete it (`Del`, `⌘⌫` on a Mac). Renaming never replaces anything, and open tabs follow it with their unsaved edits. Delete asks first and moves to the Recycle Bin or Trash; what that cannot take (too large, too deep, a drive without one) and anything in a remote project, which has no trash, is deleted for good only after you confirm exactly that. The same menu copies a path or its path relative to the project, and excludes a file or folder from the tree: exclusions are kept per project, shared by its worktrees, and only change this tree (agents and git still see the files). A click previews a file in a tab beside the chats (the next click replaces it); a double-click or an edit keeps the tab. Files open in a Monaco editor and save themselves as you work: when you pause typing, switch tabs or windows, close a tab or window, and before agents and git use them (turn it off in Settings > Editor; `Ctrl/⌘ S` always saves). The gutter marks what changed since the last commit, as you type (a green bar for added lines, the modified colour for changed ones, a red wedge where lines were removed, and the same marks on the scrollbar); click a mark to see the committed lines and Revert them (undo brings your edit back), and Mango asks before closing a tab only when it can't save it (or, with automatic saving off, whenever it has unsaved edits). If a file changes on disk while you edit it (an agent, the terminal), saving stops and asks whether to discard your edits or overwrite the file. Pictures (PNG, JPEG, GIF, WebP, AVIF, BMP, ICO) open in an image viewer that fits them to the pane and zooms (buttons, `Ctrl` + wheel, `+` / `-` / `0`); SVG files open as a picture with a Preview / Code switch, and the preview follows unsaved edits. Other binary files and text files over 5 MB are not opened.
- **Changes (tool window on the right):** git status, diffs in the main pane (side by side or one column), stage / unstage / discard, commit, fetch / pull / push, branches, history.
- **Editor:** completion as you type in every project, remote ones too, from each language's keywords, the words in the project's open files and paths, and a caret that glides (Settings > Editor turns that off; reduced motion does too). For projects on this computer Mango can also use language servers (TypeScript and JavaScript, Rust, Python, Go, C and C++, C#) for type-aware completion with automatic imports, documentation on hover, parameter hints, errors, colours for what each name is (classes and other types, methods, constants, as the server knows them: in a Unity project, `MonoBehaviour` and `Mathf` too, once the server has loaded the solution), and go to definition (`F12`, or `Ctrl/⌘` + click) within the project. In C# (Unity projects included), going to a type from a compiled library (UnityEngine, a NuGet package, .NET itself) opens the source the language server decompiles, read-only, in a tab of its own. Without a language server, go to definition works within the file. Rename (`F2`) works within the file too, and refuses names that are exported or are members other files could use, before you type a new one. Language servers can run a project's own code (build scripts, plugins), so Mango asks once per project before starting one and remembers the answer for that folder: another folder at the same path (deleted and cloned again), or a project you removed from Mango and added back, asks again. A git worktree that Mango makes for a chat follows its project's answer. Any other worktree (made elsewhere, moved, or from an older Mango) follows a no and asks once where the project said yes; a Unity VCS workspace, or another folder put where a worktree was, is asked about separately. A folder's own no always stands. A server starts with the first file that needs it and keeps running while its project is open in the window, so closing the last file does not mean loading the project again; it hears about files created, changed, renamed or deleted on disk (by an agent, a terminal, Unity, a checkout) as they happen. Settings > Editor shows which servers are installed, runs their installers in a terminal you watch, and turns them off altogether.
- **Git log (bottom panel):** the history of the folder in view as a commit graph, opened from its button at the foot of the tool stripe, `Ctrl/⌘ Alt 9` or the command palette. Branches and merges are coloured lanes, with branch, remote and tag chips on their commits. It opens on the branch you are on and follows it; show all branches, another branch or one author from the toolbar. Search the messages (or `author:name`), or type a hash to jump to it. The selected commit's message and files sit beside the log, and a file opens its diff in a tab. A commit's menu copies its hash or subject, starts a branch, or checks out a branch or the commit itself. The tab moves like a terminal's: along the panel, into the main area and back. Git only.
- **Worktrees (parallel chats):** start a chat in its own git worktree (`Ctrl/⌘ Shift N`, the caret beside "+" in the sidebar, or "New chat in a worktree" in the command palette) and it gets its own folder and branch, so several agents can change the same project at once without touching each other's files or your project folder. The worktree is made when you send the first message: Mango names a new branch after it (`fix-the-login-redirect`, with `-2` … when taken) and adds the folder beside the repository (`<repo>.worktrees/<branch>`) from the project's current commit. The same menu continues in a worktree that is already there, with a new chat. The working copy in view follows the chat in front of you: the titlebar's branch, the Changes and Files tool windows, the branch popup and new terminals all work in that chat's worktree. Worktree chats show their branch in the sidebar and a worktree mark on their tab. "Remove worktree…" in a chat's menu removes the folder and keeps the branch and its commits; it refuses while the worktree has uncommitted changes unless you confirm once more. A project opened from a linked worktree is recognised as one too. In a Unity VCS project the same commands give a chat its own **workspace** instead: a child of the current branch named after the first message (`/main/task/fix-the-login`), in a new workspace of the same repository at `<project>.worktrees/<name>`, which first downloads that branch's files (this can take a while on a big project; the chat says so while it waits). "Remove workspace…" deletes that workspace and its folder and keeps the branch; it refuses with pending changes unless you confirm once more.
- **Pull requests (tool window on the right):** the pull requests and issues linked to the chat in front of you, from GitHub or GitLab (gitlab.com or your own server; for a GitLab project the window is called Merge requests). When the agent opens one in a chat (`gh pr create`, `gh issue create`, `glab mr create`, `glab issue create`, or a GitHub or GitLab MCP tool), Mango links it to that chat and opens it beside the chats: state, title, author, branches, changes, checks and review, labels, and the description as GitHub renders it, pictures included. The tool row that created it gets a `#42` button that shows it again, and the chat's row in the sidebar leads its title with the pull request's icon, coloured by its state, and shows its number (`+1` when more are linked). While a pull request is open in the tool window, Mango keeps reading it (every 10 seconds while checks run, every minute otherwise) and lists each check, failed ones first; when all of them pass it just says so. A GitHub Actions check opens its log right there, laid out like GitHub's job page: the job's steps with their state and time, each opening to its numbered log, with `##[group]` sections folded, errors and warnings marked and colours kept. A failed step opens by itself and its first error scrolls into view; while the job still runs, its steps update every few seconds and the log follows once it finishes. The `#42` button at the top (or Esc) goes back to the pull request. Other checks open their details on their own site. Merge it from there with any method the repository allows (merge commit, squash, rebase); Mango asks once more first, and GitHub refuses if the branch got new commits since you looked. Link others by hand: a chat with nothing linked shows a field over the repository's open pull requests and issues (the link button in the header opens the same one), filtered as you type a number, a title or a branch (arrows to move, Enter to link, Esc to clear); a link, `owner/repo#12` or `#12` works too, also for closed ones (a number is looked up in the project's GitHub repository). With no chat in front, the window lists the project's open pull requests and issues with the same search field; picking one opens it there (checks, logs and merging included) without linking it to anything, and the arrow in the header goes back to the list. Details are read through the [GitHub CLI](https://cli.github.com) (`gh`), signed in with `gh auth login`; Mango never sees a token. Descriptions are sanitised before they are shown. **GitLab** works the same way through the [GitLab CLI](https://gitlab.com/gitlab-org/cli) (`glab`): merge requests are numbered `!12` and issues `#12` (GitLab counts them apart), so type `!12`, `#12`, `group/project!12` or paste a link (`…/-/merge_requests/12`, `…/-/issues/12`); a pipeline's jobs are the checks, and each opens its log, sections as steps; merge with the methods the project allows (merge or squash), with approvals shown as Approval. Sign in to gitlab.com or a self-managed server (added by its address) under Settings > Git hosting, or in an environment from its page; Mango only asks servers you added. For a remote project, Mango runs the `glab` installed and signed in inside its environment (this computer's only when the environment has none), so nothing needs installing here.
- **Browser:** real web pages in tabs beside the chats (the globe button at the right of the tab strip, `Ctrl/⌘ Shift B`, or "New browser tab" in the command palette), so a dev server's page can sit next to the chat working on it: split it right, reload, go back and forward, open the page in your system browser, or open its developer tools. Type `localhost:3000` (or `127.0.0.1:8080`, `[::1]:3000`) and Mango adds `http://`; an address with a dot gets `https://`; anything else is not searched for. Links to local dev servers (`localhost`, `127.0.0.1`, `0.0.0.0`, `[::1]`, `*.localhost`) in chats and in the terminal open in a browser tab beside the chat; other links still open in your system browser. Claude Code and Codex get browser tools for each chat: they open a page, read it (a snapshot of the page), click, type, press keys, scroll, run JavaScript, read the console and take screenshots. The first time an agent uses them in a chat, a browser tab opens beside that chat (its tooltip says which chat opened it). With Claude Code, reading the page, its console and screenshots runs without asking; everything else follows the chat's permission mode. Pages load only over http(s), never get access to Mango itself, and close with their tab (they are not restored after a restart). Remote projects get the browser too: `localhost` addresses in a remote project's browser are the environment's own, tunnelled over SSH (on the same port number here when it is free), and agents running in an environment reach the browser tools through a reverse SSH forward (an Incus proxy device `mango-browser` on the instance while Mango runs; joined environments use the SSH forward alone). Limits: screenshots work on Linux only for now; local `https` addresses in a remote project are not supported yet; the page is a native view drawn over the app, so it hides while a menu, dialog, the command palette or Settings is open, and while you drag a divider.
- **Releases (tool window on the right):** the project's GitHub or GitLab releases, newest first, and the GitHub Actions runs (on GitLab, the tag pipelines) that build them. A build that is running sits on top with its jobs as a row of steps (so does a draft whose build failed, and a run of the release workflow started by hand, shown as a trial build); the button on the tool stripe shows a turning ring while a release builds and a red cross when its build failed, also with the window closed. A release opens to its tag and commit, the workflow run with each job (running and failed ones first, with times, and about when a running build will be done, from how long the last ones took), its files grouped by platform (each `.sig` signature folded into the file it signs; click a file to download it in your browser) and its notes as GitHub renders them. A job opens its log, as in the Pull requests window. Re-run a failed build's failed jobs, or cancel a running one (Mango asks once more first); on GitLab, Retry runs a pipeline's failed jobs again and Run again starts a new pipeline on the tag. A GitLab release set for a later date shows as Upcoming, and file sizes and downloads show only where the forge reports them. Mango keeps it current: every 15 seconds while a release builds and the window is open (30 seconds while it is closed), every two minutes otherwise, never while the app is hidden. Read through the GitHub or GitLab CLI like pull requests, so it works for remote projects too; Unity VCS and Lore projects have no Releases button.
- **Unity Version Control (Plastic SCM):** a folder inside a Unity VCS workspace (it has a `.plastic` folder) uses the same Changes view, diffs and branch popup, driven by your own `cm` client. Pending changes, diffs, checkin, undo, update, changeset history, branches (`/main/...`: switch, create, rename, delete), and shelves (shelve the changes, optionally undoing them so the workspace is clean, then apply or delete a shelve from the Changes view) all work. Locks too: locked files show who holds them, a Locks section lists every lock in the repository, a file row's context menu locks a file (by checking it out, as the server's lock rules decide) or releases your own lock, and the checkin line warns when a file you are about to check in is locked by someone else. The Pull requests tool window shows its code reviews instead: the reviews of the current branch and the open ones in the repository, with status and each reviewer's verdict, and asks for a review of the branch (title and optional reviewers) through `cm codereview`; commenting and approving stay in Unity VCS. Unity VCS has no staging area: what you stage is what the next checkin takes (nothing staged takes everything), and Mango remembers that choice while it runs. Merge into the workspace from the branch popup: Mango shows what the merge changes first, leaves the result as staged pending changes to check in, and leaves merges with conflicts to the Unity Version Control app. There is no fetch, push, amend or rebase for Unity VCS in Mango. Sign in with the Unity Version Control app or Unity Hub; Mango never handles credentials.
- **Lore:** a folder inside an Epic Games [Lore](https://github.com/EpicGames/lore) repository (it has a `.lore` folder), on this computer or inside a remote environment, uses the same Changes view, diffs, branch popup and Git log, driven by your own `lore` client. Changes (each refresh scans the working tree, as `lore status --scan` does), stage and unstage, discard, commit, amend the message of a revision not pushed yet, pull (`lore sync`, which merges when the branch has diverged), push (which also publishes a new branch), the revision history with each revision's files and diffs, branches (switch, create, merge, and delete, which archives the branch on the server for everyone) and locks (as for Unity VCS: who holds what, lock a file, release your own) all work. Revisions show as `r12`; the server's side of a branch shows as `remote/<branch>`. Lore has no rebase, branch rename, worktree chats, pull requests or releases, so Mango leaves them out for Lore projects. Sign in with `lore login`; Mango never handles credentials.
- **Terminal:** a real PTY docked at the bottom, with tabs. Mango finds the shells on your machine (login shell and `/etc/shells` on Linux/macOS; PowerShell, Command Prompt, Git Bash, MSYS2/Cygwin, Nushell and WSL distributions on Windows); pick one per terminal from the arrow next to the +, and set the default, font size and cursor in Settings > Terminal. A terminal can also live in the main area, as a tab beside the chats: drag its tab out of the panel onto the tab strip or a pane (the right third of a single pane splits it), or use "Move to editor area" (the arrow in the panel's header, a tab's right-click menu, or the command palette); "New terminal in editor area" in the command palette opens one there directly. Drag it back onto the panel (or onto the strip that shows while the panel is hidden), or use "Move to panel", to dock it again. Moving keeps the same shell and its scrollback; closing the tab ends the shell, as closing it in the panel does. Like terminals in the panel, they are not restored after a restart.
- **Attachments:** paste a screenshot or copied files into the message box, pick files with the paperclip, or drop them on a chat. Mango keeps a copy in its app data folder; Claude Code gets images inline and other files by path (with read access to that folder), Codex gets images by path. Up to 10 per message, 25 MB each; large images are shrunk to fit the model's limits.
- **Pictures in replies:** when an agent's reply shows a picture with markdown (`![alt](path)`), Mango shows it in the chat if the path is a file on your computer: absolute, `file://`, or relative to the project. In a remote project the path is a file inside the environment (for example a screenshot the agent took with Chromium for agents), read there over SSH; the phone app shows them too (up to 10 MB there). Click it to open it full size. Only real PNG, JPEG, GIF, WebP, AVIF and BMP files (judged by their contents, up to 25 MB) are read, and pictures on the web are never fetched; they stay as text.
- **Languages:** English, German and Russian, following the computer's language unless you pick one in Settings > Preferences. Agent replies, git and terminal output, and errors from the backend stay as they come.
- **Voice input:** press the microphone in the message box (or `Ctrl/⌘ Shift Space`) and speak; the words appear in the box as you say them (re-transcribed every second or two), and pressing it again settles the final text at the caret (Esc discards). Speech is turned into text on your computer by OpenAI's Whisper (run in Rust with candle), in any of its ~100 languages, detected automatically. In Settings > Voice pick a model (Tiny 154 MB, Base 293 MB, Small 969 MB), download it once from Hugging Face (pinned and checksum-verified), choose and test the microphone, fix the language, and optionally send as soon as the transcript is in.
- **Notifications:** a desktop notification when a chat needs you, finishes or fails while Mango is in the background (Settings > Notifications): pick which, hide the chat's text, add a sound.
- **Remote environments:** run agents inside [Incus](https://linuxcontainers.org/incus/) containers and VMs on a server you reach over SSH (Settings > Environments, also "Environments" in the command palette and on the welcome screen). Add a server by its SSH destination (`user@host` or a `~/.ssh/config` alias, optional port and key file); all it needs is SSH access and sudo. On a plain Debian or Ubuntu server Mango installs Incus for you from the server's page (its packages, a storage pool and a network, and your SSH user in `incus-admin`), sets up an Incus that is installed but not initialised, and updates it later; the setup runs in a terminal you watch, where `sudo` can ask for your password. An existing Incus works as is, optionally with an Incus remote that points at IncusOS hosts. Nothing of Mango's keeps running on the server: every action is one `ssh … incus …` call signed in with your own SSH keys and agent, and Mango never sees a password. Create an environment (Ubuntu or Debian, container or VM, CPUs, memory, disk) and pick components to install with one click: the `agent` user and build tools, Claude Code, Codex, GitHub CLI, Node.js (official builds from nodejs.org, the current LTS or any version you pick), Java (SDKMAN for the `agent` user, with the current Temurin LTS or any vendor and version SDKMAN offers), Chromium for agents (a headless Chromium with Playwright's MCP server, registered with Claude Code and Codex there, so agents can open pages, read them and take screenshots on their own, and show you a screenshot in the chat when you ask for one), an XFCE desktop, Docker (Engine with Compose and Buildx, usable by the `agent` user; a container gets Incus nesting turned on for it, which restarts an existing one once), Tailscale, and [Lore](https://github.com/EpicGames/lore) (Epic Games' version control): its CLI, and a Lore server that runs as a service with its data in `/var/lib/lore` (both a pinned release, checked against its SHA-256). **Lore server in one click:** "New Lore server" on a server's page creates an environment called `lore` with the server installed. The other environments on that server reach it right away at `lore://lore.incus`; tick "Reachable from outside this server" (or Publish… on its page later) to reach it from this computer and anywhere else, at an address of the server you pick (its Tailscale address first, then a private one; all addresses or a public one only with a warning, because the Lore server has no sign-in: whoever reaches it can read and write) and a port (41337 unless you change it). Mango forwards UDP (what the CLI speaks) and TCP on that port into the environment, says if this computer reaches it, and when ufw, firewalld or an nftables rule on the server would block it, shows the command that opens the port (it never changes a firewall itself; a cloud provider's security group has to allow the port too). The Lore server section on its page has both URLs to copy, Stop publishing, and "Use as Lore server". Installing again updates them (Node.js to the newest release of its line; Java keeps its version and updates SDKMAN), and each install runs in a terminal you watch. Node.js and Java have a **Version** picker, in the create dialog and on the environment's page: every version from nodejs.org or SDKMAN, grouped by release line or vendor, with a search field (`21 tem`, `lts`, `22.11`); picking one on the page installs it or switches to it. Start, stop, restart and delete (you type the name to confirm), rename (Incus renames only stopped environments, so a running one is stopped and started again; its projects and chats in Mango move to the new name) and resize (CPUs, memory and disk from the environment's page, under its ⋯ menu; a disk only grows, and a VM's file system grows when it next starts), sign in to Claude Code, Codex, GitHub CLI or Tailscale with each tool's own flow in a terminal inside the environment, open a shell, view the desktop in Mango (noVNC, tunnelled over SSH, never exposed to the network), and open a project folder there (optionally cloning a repository into it). Projects also go into an environment from the usual flows: Open folder, New project and Clone repository (project menu, welcome screen, command palette) have a **Where** choice, this computer or any running environment (grouped by server, with "Shared with you" last), and Mango remembers the last one. In an environment, Open folder browses its folders in Mango's own picker (git repositories marked, or type a path), New project makes the folder there (with `git init` if you want it), and Clone runs `git clone` inside it (private repositories need the GitHub CLI signed in there). The **Environment** tool window, the bottom button on the right-hand tool stripe, shows where the active project runs: a laptop for this computer, a server for an environment, with a mark when it is stopped or can't be reached. It holds the folder, the environment's state and addresses, a shell in the terminal dock, its desktop, the CLIs' sign-ins, its components with versions and updates, and who it is shared with; it checks the environment when it opens, never in the background. Chats on that project run the agent inside the environment as the `agent` user, and the terminal opens a shell there; stopping a run stops the agent's processes in the environment too. **Dropped connections:** a run keeps going in the environment when the network or the server goes away. The chat says "Reconnecting to <environment>" and stays Working; Mango attaches to the run again as soon as the server answers (it checks every few seconds, and at once when your computer is back online or the window comes to the front), and nothing the agent wrote meanwhile is lost; messages and answers you send meanwhile go out once it is back. A run nobody is attached to for 30 minutes stops itself there. A remote terminal whose connection drops says so and starts a fresh shell in the same tab when the server is back (exiting the shell yourself still asks for Enter). The phone app reattaches its runs the same way, also after a switch between Wi-Fi and cellular or a return from the background, and says when it has no internet connection. The Changes and Files views, the chats kept in the environment and the agents' browser tools pick up again on their own too. Attachments go along too: pictures inline, and every other file (PDFs, documents, logs, archives) is put into the environment, in the `agent` user's `~/.local/share/mango/attachments` where the phone app puts its own, and the agent reads it there. The Changes view and the branch popup work there too: git runs inside the environment as the `agent` user, so commits use that user's git identity and pushes its credentials (for example the GitHub CLI signed in there); it is read a little less often than on this computer, since every read goes over SSH. The titlebar shows the project's branch there, next to a server mark that opens the Environment tool window. The Files view browses, opens and saves files inside the environment (every path stays inside the project folder), and the Pull requests view finds the GitHub repository from the git remotes in the environment, then reads and merges through the GitHub CLI on this computer. **Tailscale** is optional per server: new environments join your tailnet with the tags you set (for example `tag:mango`, so your ACLs keep them on their own network) and Tailscale SSH. They sign in through a link in the terminal, or with an auth key read from a file on the server (never by Mango). **Sharing:** give one person full access to one environment, and nothing else on the server, with a one-line `mango://join/…` link or its QR code (Sharing on the environment's page, "Share…"). Say who it is for, how they reach it (over the internet, through a port on the server that leads only into that environment, using the server's public address or its SSH host; or Tailscale, the environment's tailnet address, when the person is on your tailnet), and when access ends (1, 7 or 30 days, or never). The first share installs an SSH server in the environment, which can take a few minutes. The link is a key: it gives root inside the environment, Mango shows it only once and keeps no copy, so send it privately. Revoke any share from the same list and the link stops working. **Joining:** whoever gets a link needs no server of their own: open it in Mango, or paste it under Settings > Environments > "Join with a link" (also "Join a shared environment" in the command palette). Mango shows what it leads to and when access ends before saving anything, then connects straight into that environment; it appears under "Shared with you" with everything above except starting, stopping, deleting and sharing. "Leave" removes it and deletes its key from your computer.
- **Updates:** checks the latest GitHub release at launch and every hour; **Update** in the titlebar downloads, verifies and installs it, then restarts Mango.
- **Windows:** open a project in a window of its own, for example on a second screen: the window button on a project's row in the project menu (titlebar) or on a Recent row of the welcome screen, or "Open project in new window" in the command palette. "New window" (`Ctrl/⌘ Alt N`, the project menu or the palette) opens one on the welcome screen. A project is open in one window at a time: opening it again brings its window to the front, and the welcome screen and palette mark it "Other window". A project moves to the new window with its chats; it waits while one of its chats is still working, or while its terminals are open (a shell stays in the window that started it), and says so. Opening a project (the welcome screen's Recent list, the palette, Open folder, New project, Clone) in a window that already has projects open asks where it goes: **This window** (beside the others) or **New window**; tick "Remember my choice" to stop asking, and change it back under Settings > Preferences ("Open a project in"). Closing a window stops what still runs in it, and its projects and chats go back to the main window. Each window closes on its own: closing the main window while others are open hides it and closes its projects, and the other windows stay; closing the last window on screen quits Mango, which reopens that window's projects next time. A single chat can have a window too: drag its tab (or its row in the sidebar) out of the window and let go, and it opens in a compact window of its own right there, with its sub-agent chats; "Move to new window" in the tab's or the sidebar row's menu, or "Move chat to new window" in the command palette, does the same. A chat window shows just that chat (no sidebar, no new chats) and may be as small as 640×480. It gives the chat back, as a tab in the window that has its project (the main window when none has), when you close it, use "Return to main window" in its titlebar, or drag its tab onto another Mango window. A chat that is still working stays where it is and says so; Esc cancels a drag. Settings and the theme are shared; each window has its own layout, and only the main window's is restored next time.
- **Get started:** on the first launch, a dialog shows whether Claude Code, Codex and Git are installed and signed in, installs what is missing with each vendor's own installer (run in an embedded terminal, so you see and answer it), and signs you in. Open it again from the command palette.
- **Environment variables** per project, in Settings > Projects ("Project settings…" in the project menu, or "Environment variables" in the command palette), for local and remote projects. It lists the `.env` files at the project root (`.env`, `.env.*`, `*.env`; example and template files such as `.env.example` are left out until you add them by name with New file, as is any other name you choose). Edit a file as rows of name and value (values masked until you show them; paste `NAME=value` lines into a name to add them all) or as raw text; untouched lines, comments and quoting are kept. Edits stay as drafts until you save (`Ctrl/⌘ S`) or revert, and a file changed on disk meanwhile asks before it is overwritten. A file git doesn't ignore gets a warning and an "Add to .gitignore" button. Create and delete files there too (deleting asks first).
- **MCP servers:** give Claude Code and Codex your own MCP tool servers in Settings > MCP servers ("MCP servers" in the command palette), for every project on this computer, and per project in Settings > Projects ("Project MCP servers" in the palette). A server is a command the agent's CLI starts (with arguments and environment variables; type it as one line, quotes keep spaces in an argument) or a streamable HTTP endpoint (with headers such as `Authorization`); each one can be switched off, and given to both agents or only one. A project's own server takes the place of a global one with the same name. Servers are passed to the CLI for each chat on top of its own settings, which keep working (Claude Code's `~/.claude.json` and `.mcp.json`, Codex's `config.toml`); a Mango server with the same name as one there replaces it in Mango's chats. Changes apply from the next message. Names use letters, digits, `-` and `_` (tools are called `mcp__<name>__<tool>`); `mango-…` is kept for Mango's own servers. Environment values and headers are kept in `mcp-servers.json` in Mango's app data folder, readable only by your user (on Linux and macOS), and reach the CLI through its environment rather than its command line. Remote projects get only their own servers, which start inside the environment like their agents (a URL there is reached from inside it); servers set for all projects stay on this computer. Tool calls show in the chat as "Used server · tool".
- **Lore:** [Epic Games' version control](https://github.com/EpicGames/lore) for large projects, through your own `lore` CLI. Settings > Lore shows the CLI (installed or not; Mango installs a missing one with Epic's own installer, in a terminal you watch) and the Lore servers you saved (`lore://host`, or `lore://host:port` when the port isn't 41337), each checked from this computer: whether it answers, and on which port it does not (Lore needs TCP for listing and creating, and UDP, QUIC, for file data, on the same port), whether the name resolves, and whether it wants you to sign in (some servers need no sign-in, which it says). Sign in runs `lore login` in a terminal there; Mango never sees a token. New project offers Git, Lore or None: Lore creates the repository on a saved server (named after the project, editable) or only in the folder (offline), and says in plain words when the server can't be reached or wants a sign-in. Clone takes a `lore://server/repository` address. In an environment both run the Lore CLI inside it, signed in there (the environment needs the Lore component); a server Mango set up in an environment on the same server is reached by its inside address from there.
- **Git hosting:** Settings > Git hosting shows the GitHub CLI (`gh`) and the GitLab CLI (`glab`): installed or not (Mango can install a missing one with WinGet or Homebrew, and finds it as soon as the installer is done, without a restart), and every server each is signed in to, with Sign out. Sign in runs the tool's own sign-in in a terminal right there: github.com or a GitHub Enterprise server, gitlab.com or a self-managed GitLab server. Mango never sees a token. The GitLab servers list names self-managed servers whose projects get merge requests, issues, pipelines and releases; servers named `gitlab.…` and those `glab` is signed in to are recognised on their own.
- **Titlebar:** the project and branch widgets (the branch shows commits to push or pull and the number of changed files), a GitHub or GitLab button beside them that opens the project's repository in your browser (shown when one of its git remotes is on GitHub or on a GitLab server, with that forge's icon; the phone app has the same as a row on the project's page), the command search, an activity widget (how many chats run and how many need you, that is, wait on an approval or an answer; sub-agent chats are left out; click it for a list and jump to one with the keyboard), and, while the sidebar is hidden, a button at its left that shows it again. The tool stripe on the right edge has a button for each tool window (`Ctrl/⌘ Alt B` toggles the tool panel, reopening the tool window used last) and, at its foot, the terminal toggle and the Environment button. The theme is in Settings > Appearance and the command palette.
- **Long breaks:** after about an hour the prompt cache of a Claude Code chat expires, and its next message has the whole conversation read again. In a chat over 200k tokens (Settings > Behaviour sets how many, Settings > Projects per project) Mango then says so over the composer and offers to compact it first (what you have written goes out afterwards); writing on as usual ignores the offer, and "Not for this chat" turns it off there. Settings > Behaviour can turn it off, or compact such chats by themselves shortly before the cache expires: only local chats with nothing open (no draft, queue or running task), once per break, and only while the plan's limits are below 80%. That uses some of your limit without asking, also for chats you never return to, and compacting always can lose details.
- **Context window:** a small ring in the composer shows how full the chat's context window is (it turns orange near the point where the agent compacts by itself, red just before). Click it to see the total against the model's window and, for Claude Code, what takes the room (system prompt, tools, memory files, skills, messages, the buffer kept for compacting, free space), as `/context` shows it; **Compact** sends `/compact`. The iOS app shows the same ring in its composer, with the breakdown in a sheet. Claude Code's numbers come from its `get_context_usage` request at the end of each turn (and its prompt size during one), Codex's from the token counts it reports per request. A Claude Code chat with no reading yet (one from an older build) gets one when you open it; until a chat has a reading the ring is empty and says when it will have one. None of this spends quota.
- **Usage limits:** the usage meter in the titlebar (it shows the most used limit) (or `Ctrl/⌘ Shift U`, or the command palette) shows how much of each plan's 5-hour and weekly allowance Claude Code and Codex have used, per-model weekly limits where the plan has them, and when each window resets. Mango asks the CLIs themselves (`get_usage` for Claude Code, `account/rateLimits/read` for Codex), which spends no quota. In a remote project the numbers are the environment's: Mango asks the Claude Code and Codex installed there, which may be signed in to another account or plan than this computer's. The same limits, with their reset times, are in Settings > Agents > Usage. When a limit drops a lot before its scheduled reset (an extra reset, for example), Mango says so there until you dismiss it; it infers this from two reads, because the CLIs do not announce it.
- **Settings:** installed agents, sign in / sign out (runs the CLI's own login in an embedded terminal), default agent and permission mode, theme and color scheme (Mango, Blue, Teal, Green, Purple, Pink, Red, Slate, Uchiha, Graphite, Ink, Cocoa, Neon, Solar). Settings > Agents has a Subscription tab with the plan each agent is signed in with (Pro, Max, Plus, …), the account, and a link to manage it with the vendor. The bottom of the sidebar shows the agent of the chat on screen with its plan and one usage meter for its tightest limit (amber from 80%, red with the time until it comes back once used up, and a Sign in button when the CLI is signed out). Its menu lists every agent with its plan and account, sets the agent new chats start with, and holds Usage limits, Subscription and Sign out (named for the agent). Next to it, Help has What's new (marked with a dot after an update until you open it), Get started, Keyboard shortcuts, Report an issue, Check for updates (Update and restart once one is ready) and About, and the gear opens Settings in one click.
- **Branches:** click the branch name (titlebar or Changes view) for a JetBrains-style popup: search, update / push / fetch, local and remote branches, and per-branch checkout, new branch from, merge, rebase, rename and delete. The Local and Remote sections start folded (searching opens them); the trash button on Local deletes every local branch except the current one and `main` / `master` / `develop` / `trunk`, after a confirmation that lists them, and asks once more before deleting any with unmerged commits. A branch checked out in a linked worktree takes that worktree with it (deleting one branch too), unless the worktree has uncommitted changes or a chat is still working in it; chats that worked there go back to the project folder. Results read as a short summary, such as "Pulled 3 commits into main" with the files and lines changed, instead of git's raw output; failures keep git's own words. For Unity VCS a new branch is a child of the one it starts from (`task` from `/main` is `/main/task`), and merge asks first, listing the files it changes (rebase is git only).
- **Sidebar:** shows the chats of the project picked in the titlebar, grouped by status: Working on top, Settled and Archived at the bottom of the list, where they fold away. A chat's sub-agents fold under it (open while one of them works). The button beside "New chat" hides it (`Ctrl/⌘ B`).
- **Chat status:** Working, Settled and Archived (plus "Needs you" and "Failed" while a run needs attention). New chats and every finished turn are Working; a chat is Settled only when you press the check mark on its sidebar row, which also closes its tab and pane (press it again to go back to Working). Archive from the thread's menu in the sidebar.
- **Order:** drag chats in the sidebar to arrange them (or Alt+↑ / Alt+↓, or Move up / Move down in the menu). New chats arrive on top, and the list holds still while agents answer: activity never reorders it.
- Chat tabs, split view, per-thread drafts, command palette, dark and light themes. A split gives each pane its own tab strip, lined up with the pane under it: clicking a tab shows it in its own pane, dragging a tab onto the other strip (or "Move to the right/left pane") moves it across, and a pane whose last tab closes or moves away closes the split. Browsers an agent or a link opens go into the pane beside the chat. `Ctrl/⌘ 1–9` pick a tab of the active pane. Right-click a tab for Close, Close others, Close to the right, Close all (within its pane; files that could not be saved, or have unsaved edits with automatic saving off, stay open), Split right, Copy path for files, and Mark as settled or Archive for chats.

Mango uses the agents' own sign-in: it never sees or stores your credentials.

Chat history is saved in a SQLite database, `chats.sqlite3` in Mango's app data
folder. Saves are incremental: only the chats that changed are written, and a
reply is saved while it streams. Chats from older versions move there on first
launch. The agents keep their own session files (`~/.claude`, `~/.codex`) as usual.

Chats of a remote project are also kept inside its environment
(`~/.local/share/mango/chats/` of the `agent` user), so every computer that opens
that environment, yours or one it is shared with, sees the same chats. A change is
sent a few seconds after it happens (at least every 15 seconds while an agent
replies), and Mango looks for changes from other computers when a remote project
opens, when its window comes to the front, and every minute while it is in front.
Deleting such a chat deletes it on the other computers too. When two computers
change the same chat, the environment's copy wins, unless the chat is running
here. Chats of folders on this computer stay on this computer.

## Plugins

Plugins add slash commands, tool windows, colour schemes, checks before a message is sent and more. Browse the
official catalog, install from any git repository (a branch, tag or folder of it), or add a folder on this computer,
all in **Settings > Plugins**, where each plugin can be turned off, updated, reloaded or removed and shows its settings
and log. A plugin is trusted code with the same rights as Mango, so install only ones you trust.

The official plugins are in [`plugins/`](plugins/). Writing one: [docs/plugins.md](docs/plugins.md).

For Unity projects there is the official [Unity plugin](plugins/unity/): it recognises them and marks them in the
titlebar, hides `.meta` and generated files in Files (View options shows them), keeps each `.meta` with its asset when
you rename or delete there, gives Unity's files their icons and highlighting, and adds a Unity tool window with the
project's details, a `.meta` check and a reference search.

The official [Planner plugin](plugins/planner/) keeps tasks, bugs and notes beside your chats: boards and tables with
properties of your own, and pages linked to chats, with notes that turn Markdown into rich text as you type. With a
[planner server](plugins/planner/server/) you host yourself, collections are shared between computers and people as they
change, and items can be assigned to the people of the space, Notion-style.

## Run it

```bash
pnpm install
pnpm app          # tauri dev: starts Nuxt on :1420 and opens the window
pnpm app:build    # release build + installers
pnpm bump minor   # new version (patch, minor, major or an exact 1.2.3) in every file that holds it
```

The version you are running, with the commit it was built from, is in Settings > Preferences. What changed in each version is in Settings > Changelog (the same file as the docs site's changelog, `docs/changelog.md`).

macOS needs the Xcode command line tools. Linux needs the Tauri system packages (`libwebkit2gtk-4.1-dev`, `libgtk-3-dev`,
`librsvg2-dev`, `libayatana-appindicator3-dev`, `libssl-dev`).

Cross-compiling the Windows installer from Linux (needs `nsis`, `lld`, `llvm`,
`clang`, `rustup target add x86_64-pc-windows-msvc` and `cargo install cargo-xwin`):

```bash
pnpm tauri build --runner cargo-xwin --target x86_64-pc-windows-msvc
```

`pnpm dev` alone serves the UI at http://localhost:1420 with an in-memory mock
backend, which is handy for working on the frontend in a browser. There, agent
replies are simulated (and labelled so), and "Load demo threads" in the command
palette fills it with sample threads.

To try an agent adapter against the real CLI without the app:

```bash
node scripts/try-agent.ts claude /path/to/project "say hi" --mode ask
```

## Mobile (iOS)

`mobile/` is a separate Expo / React Native app for the iPhone and iPad: your chats in Mango's remote
environments, on the go. Join an environment by scanning its share code (on the desktop: the environment's page,
**Share…**) or opening a `mango://join/…` link, or add a server by putting the phone's own key
in its `authorized_keys` (both under Settings). Home lists your chats; New chat starts one in any project of any
environment, or any folder in it, optionally in its own git worktree. Read and continue chats with Claude Code and Codex (approvals, questions,
permission mode, model, slash commands), mark them Working, Settled or Archived, attach photos, camera shots and files (they are put into the environment, so the agent reads
every kind, and pictures are shown to it directly), dictate messages with the microphone (iOS recognizes the speech on the
phone where it can; language and "send after dictation" under Settings > Voice), see the pictures an agent shows in its replies (a screenshot it took with Chromium for agents, read from the environment; tap one to see it full screen and zoom), the files each reply changed, the run's background tasks, and review, commit and push the changes. Pull requests and issues linked to a chat (the ones an agent opened, or any you link by link, `owner/repo#12` or `#12`) open on their own screen, as in the desktop's Pull requests view: state, branches, size, review, labels, the description, and each check, where a GitHub Actions job opens its log step by step (failures open by themselves); an open pull request merges from there (with the methods the repository allows, after a confirmation), and it stays current while you look. Changes can open a pull request for the branch (push, then `gh pr create --fill`) and links it to the chat. A project's **Releases** open from its screen, as in the desktop's Releases view: builds under way on top, then every release; one opens to its tag and commit, the workflow run with each job (a job opens its log), about when a running build will be done, its files by platform (tap one to download it in the browser) and its notes; re-run a failed build's failed jobs, or cancel a running one (tapped twice). The project's row says what is building, what failed, or the latest release, and the screens stay current while you look. All of it goes through the GitHub CLI signed in inside the environment, and only github.com.
Home lists your projects as folders (open one for its chats and changes), or every chat newest first if you prefer. Settings is a list of categories, as on the desktop, and each opens its own screen with a tab strip to jump to the next: Chats (what new chats start with: permission mode and agent; what a chat shows of the tools an agent runs: all, only failures, none, or Zen; whether a message sent mid-run queues or steers; how Home lists chats), Confirmations (whether archiving and deleting ask first), Appearance (theme, ten color schemes, interface and code fonts, text size, corners and animations, with a live preview), Notifications (when a chat needs you, finishes or fails, while iOS keeps the app awake), Voice, Environments, Agents (each agent's sign-in and plan usage in an environment, read from the CLIs, nothing is spent), Archive (restore or delete archived chats) and About. While a chat or a project's list is open, the phone looks at the environment every few seconds, so a chat the desktop is running shows as "Working on another computer" (and its new messages appear, and the mark goes when it ends) without a pull to refresh. It only watches: no notification, and nothing is sent to that run.
The phone speaks SSH itself
(SwiftNIO SSH, keys in the Keychain, host keys pinned) and runs the same commands in the environment as the
desktop, so chats sync both ways with every computer that opens it.

```bash
cd mobile
pnpm install
pnpm web             # the UI in a browser with a simulated environment (no SSH there)
pnpm ios             # a development build on the iOS simulator or a connected iPhone (needs Xcode 16.3+)
pnpm typecheck && pnpm test
npx eas-cli@latest build --profile development --platform ios   # or build it in the cloud with EAS
```

TestFlight builds ship from GitHub Actions on a `mobile-vX.Y.Z` tag; see
[Shipping the iOS app](https://reapermaga.github.io/mango/development/mobile-release).
